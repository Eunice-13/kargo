# Smart Combined Delivery — Phase 1

Status: architecture and eligibility foundations only. No live migration has
been applied. No buyer request, seller approval, shipping-fee, payment, email,
or notification UI/workflow is enabled in this phase.

## Existing architecture

- `orders` is the reservation and inventory allocation record. It references
  `buyer_id`, `seller_id` and `batch_product_id`; the product references its
  batch. Quantity and unit prices determine generated `total_amount`.
- Claim RPCs preserve inventory and waitlist rules. Buyer-shouldered delivery
  starts in `shipping_state = waiting_for_seller`, with `deadline_paused_at`.
- `set_order_shipping_fee` adds one per-order fee and resumes the exact stored
  interval `reservation_expires_at - deadline_paused_at`. The expiration sweep
  skips paused reservations and offers released stock to the waitlist.
- `reserved_payment_method` serves as the current fulfillment discriminator:
  `Cash on Meetup` has no buyer-shouldered shipping; other methods use delivery.
  This phase additionally requires the same exact reserved payment method.
- Orders store map coordinates, URL and a human-readable address. They do not
  have a validated shared destination identity. The old `addresses` table was
  removed by `202609300002_remove_unused_features.sql`. Location search result
  IDs are not persisted, and coordinates alone cannot distinguish apartments.
- `payments.order_id` references exactly one order. Standard submission and
  review RPCs update that one order. Insufficient and rejected payments retain
  their own history and deadlines. Extension requests use the existing modal,
  RPC and seller decision workflow.
- Existing `group_orders` are multi-buyer commitments with a leader, pricing
  discounts, and checkout-created reservations. They are not a delivery group
  for independently claimed reservations. Their payment RPCs cannot be called
  for a new delivery group without rewriting ownership and accounting.
- In-app notifications use `notifications`; email uses `pending_emails` and
  the existing dispatcher. No new notification infrastructure is needed.

## Implemented foundations

1. `delivery_destinations`: immutable buyer-owned coordinate + full-address
   snapshots. `orders.delivery_destination_id` is nullable, with an owner FK.
   No existing reservation is backfilled from a string, nearby coordinates,
   or matching URLs. No public write or confirmation RPC is exposed yet.
2. `combined_delivery_groups`: buyer/seller/batch/destination/method context.
   A nullable `numeric(12,2)` shipping fee exists in one place. A Phase-1 check
   requires it to remain NULL: no new group can accidentally become payable.
3. `combined_delivery_members`: existing order references, immutable original
   line subtotals and timer budgets, and historical release timestamps. A
   partial unique index permits at most one active group per order. Deferred
   checks require at least two members before commit. Orders and inventory
   are not copied or re-reserved.
4. `combined_delivery_events`: append-only creation, membership and terminal
   state audit records generated by database triggers.
5. Candidate and eligibility RPCs plus read-only TypeScript service adapters.
   The frontend eligibility helper mirrors the DB rules for later suggestions;
   it does not authorize grouping. Direct client writes to the new tables and
   the order's destination-reference column are denied.
6. RLS scopes groups/members/events to the buyer and seller. Destination owners
   can read their own snapshots; sellers only see snapshots for their groups.
   Helpers and the internal candidate view are not callable/readable by clients.

## Eligibility rules

Require two or more distinct existing reservations with the same buyer,
actual seller ID, batch ID, explicitly confirmed destination ID, delivery
method, and exact reserved payment method. Require:

- `payment_pending` only; no paid, cancelled, expired, submitted or insufficient
  orders, and no payment records at all (even rejected proofs are excluded).
- Shipping accepted, `waiting_for_seller`, paused deadline, no fee (even zero),
  and no fee-assignment timestamp. Location-correction orders are excluded.
- Positive original time budget: expiry must be later than pause time. A
  paused reservation whose wall-clock expiry is in the past remains valid.
- No existing multi-buyer group order or active combined-delivery membership.
- Destination snapshot still exactly matches the stored pin and full address.

Cross-batch grouping is deliberately rejected: the current batch dates do not
establish that two batches have compatible dispatch/arrival schedules. No
proximity or fuzzy address matching is performed.

Legacy reservations remain ineligible until a later explicit buyer confirmation
flow establishes their shared destination. Phase 2 must show all original pins
and full addresses (including unit/building details), require a single destination
confirmation, and bind the snapshot inside the request transaction. It must not
silently repin reservations to make them eligible. URL-only reservations need a
resolved, explicitly confirmed pin first. No address confirmation UI exists yet.

## Transactions and safety

The preview RPC authenticates an active buyer, rejects unavailable/other-buyer
IDs without leaking their contents, and locks owned orders in sorted order.
Preview results are advisory after the transaction ends. Phase-2 creation and
Phase-3 approval MUST revalidate within their mutation transaction.

Member insertion locks the underlying order, then the group, and rechecks its
current state and matching context. The active-membership unique index is the
last defense against overlapping requests. The rule helper is volatile so a
recheck after waiting for a row lock sees newly committed changes.

While membership is active, order updates other than `updated_at` and individual
payment inserts are rejected at the table boundary, including calls through old
RPCs. No client-side flag or settable session variable bypasses these guards.
Shipping and payment integration must provide a narrowly authorized group-aware
transaction in later migrations before those states are enabled.

Snapshot changes on an ungrouped reservation invalidate its destination binding;
existing location-correction RPCs continue to work. Group identity and original
member snapshots cannot be rewritten. Terminal transitions release memberships
and preserve original orders, quantities, fees, and timer budgets.

No new deadline duration or reset is introduced. Phase 1 accepts only reservations
already legitimately paused for seller shipping review. Group creation/rejection
cannot refresh that budget. Future payment readiness should resume the shortest
remaining member budget atomically; seller approval is needed for this proposed
rule in Phase 3. Paid/part-paid/rejected-proof orders and repeated regrouping after
fee finalization are excluded. Future request-level anti-spam/rate limiting is
still to be designed in Phase 2.

## State workflow and remaining integration

Implemented foundation states are `pending_approval`, `rejected`, `cancelled`
and `invalidated`. Only pending groups may transition to a terminal state.
There is no authenticated mutation RPC yet. The later workflow is:

`pending_approval -> awaiting_shipping_fee -> ready_for_payment -> awaiting_verification -> paid`

Only after implementing the relevant mutations should a later migration widen
the state and fee constraints. Rejection must leave individual shipping review
paused for the same reason as before, not reset or cancel the reservations.
Individual cancellation/address-correction handling for an active request must
invalidate/release the group transactionally before applying the original action.
There is currently no active request UI, so the Phase-1 guards do not interrupt
existing normal orders.

**Payment blocker:** the ordinary proof/review APIs apply to one order only.
Phase 4 needs a reliable delivery-group/payment relationship, one authoritative
combined amount (sum of member item subtotals + one group fee), and dedicated
submission/review RPCs updating all members atomically. Reuse the manual proof
upload and verification UI, not the multi-buyer group's ownership model. Update
buyer/seller projections, histories, rejection deadlines, and expiry/waitlist
handling before enabling group payment. Individual member payments must stay
blocked; no frontend-only combined total is sufficient.

Phase 2 will add request creation, destination confirmation, duplicate-request
handling and seller notification using the existing notification tables. Phase 3
will add seller review/revalidation and one fee. Phase 4 will add payment and
notification integrations, including preventing per-order email duplication.
Phase 5 will validate full workflows, responsiveness and concurrency.

## Deployment, rollback and validation

- Up: `supabase/migrations (to update profile database name)/202610200002_combined_delivery_foundations.sql`
- Down: `supabase/rollbacks/202610200002_combined_delivery_foundations.sql`
- Rollback is transactional and refuses to run if destination/group history
  exists. No historical records are dropped to reverse a deployed feature.
- Unit/regression tests: `node --test tests/combinedDeliveryEligibility.test.ts tests/claimExpiry.test.ts tests/claimPaymentState.test.ts tests/orderPaymentState.test.ts tests/paymentVerificationState.test.ts`
- DB integration tests: `psql "$LOCAL_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/combined_delivery_foundations.sql`
  Run only on local Supabase after migrations. Fixtures and changes roll back.
  Covers eligibility, participant isolation, denied client writes, membership
  uniqueness/minimum size, audits, rejection, and individual fee/payment guards.
- This environment has no PostgreSQL client/server or Docker. SQL migration,
  RLS/trigger tests and true concurrent transactions cannot be executed here.
  Do not enable request creation until the DB tests pass on local/staging.
- No migration was applied to the linked/live Supabase database.

## Strict V1 batch restriction

Only the exact same valid database batch ID is permitted. No batch-name
comparison, cross-batch schedule check, seller override or exception exists.
The frontend policy is isolated in `batchEligibility.ts`; SQL uses
`combined_delivery_batch_reasons` and `assert_combined_delivery_batch`.
Both return explicit invalid-ID/different-batch feedback. Database UUID types
and FK joins establish validity, including actual batch existence.

The preview and member-insert boundary use the centralized policy. Group
updates recheck the current active members against the immutable group batch;
a changed product-to-batch relationship invalidates a stale preview. Batch and
product rows are locked during authoritative validation. When Phase 2 adds the
request RPC it must validate within the membership transaction; when Phase 3
adds approval it must retain the group-update assertion before transition.
Those endpoint workflows are not implemented or enabled in Phase 1.

SQL regression fixtures include two batches with identical display names,
cross-batch member insertion, stale group revalidation and missing identities.
Future cross-batch proposals require a separately reviewed policy version;
there is no runtime bypass switch in V1.
